## 一、必答

### 1. 死锁是什么？用你自己的话说，不许抄定义。

答：

```
两个或多个线程各自拿着别人需要的一把锁，又都在等对方手里那把锁，结果谁都不肯放、谁也无法继续前进，程序就僵在那里不动了。
```

### 2. 四个必要条件分别是哪四个？每一个用一句话解释。

1. 互斥 ：一份资源同一时刻只能被一个线程占用。
2. 请求并保持（占有且等待） ：线程已经拿着锁，同时还去申请新锁，且申请不到也不释放手里的。
3. 不可剥夺 ：锁没被占用者主动释放前，别人不能强行抢走。
4. 循环等待 ：存在一条"线程 A 等 B 的锁、B 等 A 的锁"的环形等待链。

### 3. 为什么「破坏其中任意一个」就能避免死锁？四个里哪个在工程里最容易破坏？

答：

```
四个条件必须 同时成立 才可能死锁，缺一个就构不成环，所以破坏任意一条即可避免。
工程上 最容易破坏的是第 4 条（循环等待） ：给所有锁定一个全局统一的加锁顺序，大家都按同一顺序拿锁，环就构造不出来。第 1 条互斥通常改不了（锁的本质就是互斥），第 3 条强行剥夺代价大，第 2 条需要"一次申请所有锁"或超时回退，成本较高。
```

### 4. 死锁、活锁、饥饿。用三句话说清区别。

答：

```
死锁 ：互相等锁，谁也不动，彻底卡死。
活锁 ：没被阻塞，但一直在"谦让/重试"中反复空转，状态不停变、事情一直没进展。
饥饿 ：某个线程长期抢不到锁/资源，其他线程一直插队，它被"饿"着。
```

## 二、排查（面试真正想听的）

### 5. MySQL 里发现死锁，看什么？

- 报错号是多少？
- 看哪个命令的哪一段？
- 那一段里你要找什么关键信息？

答：

```
报错号： 1213 （Deadlock found when trying to get lock, try restarting transaction）。
看命令：SHOW ENGINE INNODB STATUS\G，看其中  LATEST DETECTED DEADLOCK  那一段。
关键信息：两个事务各自持有的锁、正在等什么锁、涉及的 SQL 和索引、WAITING FOR THIS LOCK TO BE GRANTED 与 HOLDS THE LOCK(S) 这两行，找出环形等待的方向。
```

### 6. Java 里发现死锁，敲哪两条命令？看到什么字符串就确认了？

答：

```
jps -l：先列出 Java 进程拿 PID。
jstack <pid>：输出线程栈。
看到  Found one Java-level deadlock:  即可确认，下面会列出 waiting to lock 与 locked 的线程对应关系。
```

### 7. 看到 `Found one Java-level deadlock:` 之后，你要向面试官汇报哪三件事？

答：

```
哪两个（或多个）线程互锁，各自持有哪把锁、在等哪把锁（从栈里的 locked / waiting to lock 读出）；
是什么代码路径导致加锁顺序不一致（定位到具体方法/行号）；
怎么改：统一加锁顺序，或改用 tryLock 超时、缩小锁粒度、用无锁/单锁化设计。
```

## 三、必须自己举的例子

### 8. 举一个「A 先锁 X 再锁 Y、B 先锁 Y 再锁 X」导致死锁的场景

写出两个线程各自的加锁顺序（伪代码），以及为什么必然卡死：

```
// 线程 A
synchronized (X) {
    // 拿到 X
    synchronized (Y) { ... }   // 等 Y
}

// 线程 B
synchronized (Y) {
    // 拿到 Y
    synchronized (X) { ... }   // 等 X
}
```

### 9. 怎么改才能不死锁？给出至少两种改法。

答：

    统一加锁顺序 ：A、B 都按"先 X 后 Y"的固定顺序拿锁，环构造不出来（破坏循环等待）。
    用 tryLock 超时 ：拿不到就释放已持有的锁并回退/重试，避免无限等（破坏请求并保持）。
    一次性申请全部锁 ：先判断两把锁都可用再同时拿（破坏请求并保持）。
    合并成一把锁或缩小临界区 ：干脆不需要同时持有两把锁（破坏互斥或去除嵌套）。

## 四、自测（闭卷）

1. 死锁四个条件，少一个行不行？
    不行。四条件是"与"关系，缺一即不构成死锁。
3. 为什么「按固定顺序加锁」能避免死锁？
    所有线程按同一全序拿锁，就不可能出现 A 等 B 的锁、B 又在等 A 的锁这种反向环，循环等待被破坏。
5. `innodb_lock_wait_timeout` 默认多少秒？超时报什么错？
    默认  50 秒 ；超时报  1205 （Lock wait timeout exceeded; try restarting transaction）。注意：这是 锁等待超时 ，不是死锁（死锁是 1213，由 InnoDB 主动检测并回滚一方，不需要等满 50 秒）。
7. 为什么「条件字段没索引」会让行锁变表锁，从而放大死锁概率？

```
没有索引就没法定位到具体行，InnoDB 只能扫描整张表并给扫描到的所有行/间隙加锁，锁的范围急剧扩大，多个事务更容易在同一片行上交叉等待，死锁概率随之上升。
```

## 五、一句话总结

> 如果面试官问「你遇到过死锁吗」，你打算怎么答（30 秒）？

```
"遇到过。线上有一次接口偶发卡死，jstack 一看 Found one Java-level deadlock，两个线程对两把锁的加锁顺序相反，形成循环等待。我们统一了全局加锁顺序，并对并发更新那段改成 tryLock 带超时回退。之后同类问题没再出现。排查套路是：jps 找 PID → jstack 看栈 → 找互锁线程 → 定位加锁顺序 → 统一顺序或用超时。"
```
