## 一、必答

### 1. 一次网络读数据，实际要等两件事。是哪两件？

答：

```
等待数据就绪 ：等数据从网络到达网卡，再被拷到内核缓冲区（socket 接收缓冲区）；
把数据从内核缓冲区拷贝到用户空间 （也就是从内核 copy 到你的程序内存）。
这两步是所有 IO 模型讨论的基础，五个模型的差别就在"这两步谁能省、谁在等"。
```

### 2. 五种 IO 模型分别是哪五种？每一种「第一阶段（等数据）谁阻塞、第二阶段（拷贝）谁阻塞」写清楚。

| 模型          | 等数据                 | 拷贝                 | 系统调用                                 |
| ----------- | ------------------- | ------------------ | ------------------------------------ |
| 阻塞 IO (BIO) | 阻塞                  | 阻塞                 | `recvfrom`（全过程阻塞）                    |
| 非阻塞 IO      | 不阻塞（轮询，返回 EAGAIN）   | 阻塞                 | `recvfrom` 反复调                       |
| IO 多路复用     | 阻塞（select/epoll 上等） | 阻塞                 | `select`/`poll`/`epoll` + `recvfrom` |
| 信号驱动 IO     | 不阻塞（注册信号后返回）        | 阻塞                 | `sigaction` + 数据到后回调再 `recvfrom`     |
| 异步 IO (AIO) | 不阻塞                 | **不阻塞** （内核全做完才通知） | `aio_read`                           |

### 3. 前四种为什么都算「同步 IO」？只有哪一种算真正的异步？

答：

```
因为 前四种在"数据从内核拷到用户空间"这一步，都会阻塞调用线程 ——线程必须亲自等着拷贝完成才能继续。从这个意义说，真正的"IO 操作"（拷贝）由调用线程参与，所以是同步的。
只有异步 IO（AIO）是真异步 ：应用发起 aio_read 后立刻返回，内核把"等数据 + 拷贝"全做完，再通过信号/回调通知应用。整个 IO 过程应用线程从未阻塞。
```

### 4. 「同步/异步」和「阻塞/非阻塞」是同一维度吗？各用一句话说清。

答：

```
不是同一维度。
同步/异步 ：说的是" 最终结果谁来完成 "。调用方自己等结果 = 同步；别人做完通知你 = 异步。
阻塞/非阻塞 ：说的是" 发起调用后线程要不要挂起 "。挂起 = 阻塞；立刻返回 = 非阻塞。
一句话： 阻塞/非阻塞描述"线程状态"，同步/异步描述"结果通知方式" ，可以组合出四种情况，比如非阻塞 IO 就是"非阻塞发起，但同步等待拷贝"。
```

## 二、select / poll / epoll（必答）

### 5. select 的三个硬伤是什么？

答：

```
fd 数量上限 1024 ：fd_set 是固定长度的位图，由 FD_SETSIZE 决定，默认 1024。
每次调用都要把整个 fd 集合从用户态拷到内核态 ，且返回后要重新设置（因为内核会修改 fd_set），开销随 fd 数线性增长。
返回后要 O(n) 遍历所有 fd 才知道谁就绪 ，内核和用户都要扫一遍。
另外它还 不支持复用 、 跨平台但性能差 。
```

### 6. epoll 为什么在「连接多但活跃少」时远胜 select？说清它的两个数据结构各干什么。

答：

```
两个核心结构：
红黑树（rbtree） ：在 epoll_ctl 时存放 所有被监听的 fd ，负责高效的增删改查（O(log n)），这就是"注册表"。
就绪链表（ready list） ：当某个 fd 数据就绪，内核通过回调把这个 fd 挂到就绪链表中。epoll_wait 直接从链表取， 返回的只有就绪的 fd ，复杂度 O(活跃数) 而不是 O(总 fd 数)。
这就是"连接多但活跃少"场景的优势：多少连接都无所谓，只处理真正活跃的那几个。
```

### 7. 水平触发（LT）和边缘触发（ET）差在哪？ET 为什么必须配「非阻塞 + 循环读到 EAGAIN」？

答：

```
LT（水平触发） ：只要缓冲区里 还有数据 ，epoll_wait 每次都会通知你。哪怕你没读完，下次还会提醒。
ET（边缘触发） ：只在 状态变化的那一瞬间 （数据从无到有）通知一次。之后就算还有数据没读，也不会再通知。
所以 ET 模式下， 你必须在收到通知后一次性把数据读完 ，否则剩下的数据永远等不到新通知：
必须非阻塞 ：循环读要一直读到返回 EAGAIN（表示当前没数据了），如果 fd 是阻塞的，读到没数据时会 卡死 在 read 上。
必须循环读 ：因为只通知一次，读不干净就丢数据；循环到 EAGAIN 才代表"真的读空了"。
```

## 三、必答场景题

### 8. Redis 是单线程的，为什么还能扛十万 QPS？

答：

```
纯内存操作 ，不走磁盘，每次读写都是内存级速度；
用了 IO 多路复用 （epoll），单线程就能同时处理大量连接，不会因为某个连接阻塞整个线程；
单线程避免了锁竞争和上下文切换 开销，CPU 缓存友好；
数据结构高效 （如跳表、哈希表），命令执行本身极快；
实际瓶颈在网络和内存带宽，而非 CPU，单线程足够。
注意：Redis 6.0 之后网络 IO 可以多线程，但 命令执行仍是单线程 。
```

### 9. Tomcat 的 NIO 模式、Netty、Nginx、Redis —— 它们共同依赖操作系统的哪个机制？

答：

```
IO 多路复用（Linux 下是 epoll） 。它们都是"少量线程 + epoll 监听大量连接"，用事件驱动的方式避免"一连接一线程"的资源浪费。
```

## 四、自测（闭卷）

1. 五种 IO 模型按「阻塞程度」排一遍。
    阻塞 IO → 非阻塞 IO（等数据不阻塞但拷贝阻塞）→ IO 多路复用（类似阻塞，但一次等多个）→ 信号驱动 IO（等数据不阻塞）→ 异步 IO（全程不阻塞）
    严格说阻塞和非阻塞不是一条连续刻度，但按"应用线程被挂起的程度"排序，大体是上面这个顺序，异步 IO 最"轻"。
3. select 为什么有 1024 上限？
    因为它用 fd_set 位图表示要监听的 fd，fd_set 是 固定长度 （默认 1024 bit），由内核编译时的 FD_SETSIZE 常量决定，无法动态扩容。这也是 poll/epoll 出现的原因之一。
5. epoll 的红黑树和就绪链表分别存什么？
    红黑树 ：存所有 注册被监听 的 fd（持久化，不因某次 wait 清空）。
    就绪链表 ：存 当前已经就绪、等待被取走 的 fd（一次 wait 消费后清空）。
7. 什么是「惊群」？怎么解决？

```
惊群（thundering herd） ：多个进程/线程同时在同一资源上等待事件，当事件发生时 全部被唤醒 ，但只有一个能处理，其余白唤醒、白白竞争，造成性能浪费甚至争抢。
解决：
内核层面 ：epoll 用  EPOLLEXCLUSIVE  标志（Linux 4.5+），只唤醒一个等待者；
应用层面 ：Nginx 用 accept 互斥锁，或使用 SO_REUSEPORT 让内核按哈希分配连接；
Java NIO 里则是一部分 Reactor 模式，靠"单个 selector + 事件分发给 worker"避免多线程抢同一个事件。
```

## 五、和 Java 的关系（必答）

### 10. Java NIO 的 `Selector` 在 Linux 上底层是什么？Netty 为什么比「一个连接一个线程」强？

答：

```
底层就是 epoll 。Java 里 Selector.open() 在 Linux 上对应 epoll 实例，select() 对应 epoll_wait，注册对应 epoll_ctl。JDK 用 epoll 实现了 NIO 的选择器。
Netty 强在模型 ：一连接一线程时，连接数上千就意味着上千线程， 线程上下文切换和栈内存开销巨大 ，CPU 大量时间花在切换上而不是处理数据。Netty 基于  Reactor 模式（主从多线程） ，用少量线程 + epoll 监听成千上万连接，只对有事件的就绪连接做处理，线程复用度高、内存省、切换少，所以并发能力远超传统 BIO。
```

## 六、一句话总结（面试时你就说这句）

```
五种 IO 模型的差别，本质是'等数据'和'拷贝数据'这两个阶段谁在阻塞；前四种都要应用线程自己等拷贝完成，所以是同步 IO，只有异步 IO 让内核全程代劳。而高并发靠的是 epoll 这种多路复用机制，把大量连接交给少量线程，用事件驱动替代一连接一线程的阻塞等待。
```
